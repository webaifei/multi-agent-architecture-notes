# 00 · 概念：先把「多 agent」这四个字拆开

这一篇不写代码，只建立一套词汇。后面三章会反复用到它，词汇统一了，三套系统的差别才看得清。

## 一、一个 agent 是什么

先给结论：

> **agent = 循环 + 上下文 + 工具 + 策略**

四样东西缺一不可：

| 组成 | 是什么 | 决定什么 |
| --- | --- | --- |
| **循环 loop** | `while (true) { 问模型 → 执行工具 → 回填 }` | 能不能多步完成任务 |
| **上下文 context** | 一个 messages 数组 | 模型「知道」什么、成本多少 |
| **工具 tools** | 模型能申请的副作用（读文件、跑命令、调 API） | 能改变什么 |
| **策略 policy** | 轮数上限、超时、权限、审批、截断 | 会不会失控 |

模型本身**不是** agent。模型只会做一件事：看着当前上下文，输出「一段话」或「一个工具调用申请」。它不执行、不记忆、不判断对错。**执行、记录、校验，全是循环的活。**

第 1.1 节那个 60 行的文件，就是一个完整的 agent。

## 二、单 agent 的三个天花板

多 agent 不是潮流，是被三个硬约束逼出来的：

1. **上下文天花板**
   一个任务的探索过程会把 messages 撑爆：读 30 个文件、跑 20 条命令，中间产物全是垃圾，但全留在上下文里，又贵又干扰。
   典型做法：把「探索」外包出去，只把结论拿回来。**这就是上下文隔离。**

2. **串行天花板**
   一次只能干一件事。哪怕三件事互不依赖（分别研究三个模块），也只能排队。
   典型做法：并行开多个执行体。**这就是 fan-out。**

3. **专业化天花板**
   同一个系统提示词很难同时擅长「写代码」和「当审查员」。让审查员带着「挑错」的立场独立看一遍，比同一个 agent 自我审查有效。
   典型做法：不同角色的独立 agent。**这就是角色分工。**

注意：这三条都是**工程收益**，不是玄学。判断一个多 agent 设计好不好，就看它有没有真的换到这三样之一。换不到，就是白白增加复杂度和成本。

## 三、多 agent 的四个核心问题

任何多 agent 系统，无论包装成什么名词，都要回答这四个问题。**这就是本仓库的分析框架。**

### 1. 拓扑：谁创建谁？

```
① 主管-工人 (orchestrator-workers)        ② 流水线 (pipeline)

      ┌────────┐                            ┌─────┐   ┌─────┐   ┌─────┐
      │ 主管    │                            │ A   │ → │ B   │ → │ C   │
      └───┬────┘                            └─────┘   └─────┘   └─────┘
    ┌─────┼─────┐                            上一环的输出 = 下一环的输入
    ▼     ▼     ▼
  工人A  工人B  工人C                          适合：研究→写→审 这类阶段明确的活
  适合：可拆分的独立子任务

③ 对等团队 (peer / team)                  ④ 递归 (recursive)

  ┌──────── 共享任务板 ────────┐              agent ──spawn──> agent
  │  [任务1] [任务2] [任务3]   │                        └──spawn──> agent
  └──┬───────┬───────┬────────┘
     ▼       ▼       ▼                        自己也能是别人 spawn 出来的
   成员A   成员B   成员C                       适合：搜索/证明这类可递归分解的问题
  适合：任务边界事先不清楚，边干边分
```

### 2. 隔离：子 agent 能看到什么？

光谱从「完全隔离」到「完全继承」：

| 模式 | 子 agent 的初始上下文 | 代表 |
| --- | --- | --- |
| **全新** | 只有 自己的系统提示词 + 这次的任务提示词 | Claude Code 的普通 subagent |
| **精选** | 全新的 + 少量父级信息（项目说明、git 状态） | Claude Code 会给 CLAUDE.md |
| **继承** | 父级已完成的对话历史（fork） | DeepSeek Harness 的 `subagent-fork-in-process` |
| **共享** | 直接读写同一块黑板/任务板 | Agent Teams 的共享任务清单 |

隔离越强 → 上下文越省、越不容易跑偏；越弱 → 子 agent 越「懂你」，但越贵。
**隔离方式决定成本，也决定子 agent 能不能并行**——共享可变状态的 agent 很难真正并行。

### 3. 通信：怎么交换信息？

从弱到强：

- **一次性返回值**：父 agent 只收到子 agent 的最后一条消息，中间过程全丢。（Claude Code 默认）
- **可续对话**：拿到子 agent 的 id/handle，之后还能追问。（DeepSeek Harness 的 continuable subagent）
- **异步消息**：成员之间互相发消息，不限于父子。（Agent Teams 的 SendMessage）
- **共享状态**：不互相发消息，都去改同一块黑板 / 任务板。（共享任务清单）

### 4. 收敛：谁来决定「结束了」？

- 主管聚合：所有工人交活，主管拍板；
- 预算耗尽：轮数/时间/token 到顶就停（**所有系统都有这一条兜底**）；
- 任务板清空：任务全部 complete；
- 验证通过：审查 agent 说 OK（对抗式验证）。

> 一句话总结：**拓扑 × 隔离 × 通信 × 收敛**，就是一个多 agent 架构。
> 后面每章结束，我们都用这四个格子给系统填一次表。

## 四、三家系统的第一印象

| | Codex | Claude Code | DeepSeek Harness |
| --- | --- | --- | --- |
| 执行体是什么 | **进程**（Rust 写的 CLI，可 app-server 协议驱动） | **会话内的子循环**（一个 Markdown 文件定义一个角色） | **能力接缝**（Service/Provider/Consumer，可进程内可跨进程） |
| 子 agent 怎么来 | 起一个新进程/云端任务，通过协议通信 | 主 agent 调用 `Agent` 工具，按 `.claude/agents/*.md` 的声明装配 | provider 注册到 `ctx.subagents`，模型用工具调用 |
| 上下文默认 | 新会话 | 全新（只有自己的系统提示词 + 任务提示词） | 可选：全新 / fork 历史 / 跨进程 |
| 最强的地方 | 沙箱、审批、工具层极其扎实 | 声明式定义 + 上下文隔离做得最干净 | 任务板、持久消息、写范围、脚本化 fan-out |
| 最像什么 | 「一个能开子进程的工程师」 | 「一个会叫同事帮忙的项目经理」 | 「一个有组织架构的公司」 |

## 五、怎么读这个仓库

每一章的节奏固定：

```
一个最小可运行版本  →  补上一个真实机制  →  对照真实源码  →  动手练习
```

跑代码永远比读代码快：

```sh
node chapter1-codex/step1-agent-loop.mjs      # 默认 Mock，输出确定
node chapter1-codex/step1-agent-loop.mjs --real   # 换成真实模型
```

> 提醒：本仓库的 Mock 不是「假实现」。它是**确定的模型替身**——接口和真实模型完全一致，
> 只是把「问网络」换成「查剧本」。这样教学时可复现，换 `--real` 就能验证同样一套循环对真实模型也成立。
